# Worker Contract

## Status

Draft

## Purpose

The Worker Contract defines the interface between Hermes Core and execution workers.

Workers are ephemeral execution units. They do not own workflow state, scheduling decisions, permissions, or persistent memory.

Hermes Core is responsible for:

- workflow orchestration
- state transitions
- capability selection
- policy enforcement
- artifact storage
- execution history

Workers are responsible for:

- interpreting assigned objectives
- producing artifacts
- reporting observations
- recommending next actions

---

# Worker Request

Hermes Core provides workers with a structured execution package.

Example:

```json
{
  "execution_id": "uuid",
  "workflow_id": "uuid",

  "role": "developer",

  "objective": {
    "description": "Implement OAuth refresh token support",
    "acceptance_criteria": [
      "Tests pass",
      "API remains backward compatible"
    ]
  },

  "context": {
    "artifact_refs": [
      "requirements_v1",
      "architecture_v2"
    ],

    "memory_refs": [
      "project_conventions_v4"
    ]
  },

  "constraints": {
    "allowed_tools": [
      "filesystem",
      "git",
      "test_runner"
    ],

    "max_iterations": 3
  }
}
```

## Request Fields

### execution_id

Unique identifier for this worker invocation.

Used for:

- logging
- tracing
- recovery
- audit history

### workflow_id

Identifier for the parent workflow execution.

Multiple worker executions may belong to the same workflow.

### role

The capability being requested.

Examples:

- architect
- developer
- reviewer
- verifier
- researcher

Workers are selected by role, not by model name.

### objective

Defines what the worker is expected to accomplish.

The objective contains:

- description
- acceptance criteria
- relevant constraints

### context

Contains references to information Hermes Core has selected.

Workers do not independently search all memory or artifacts.

Hermes provides:

- relevant artifacts
- applicable memory
- project context

### constraints

Defines operational boundaries.

Examples:

- allowed tools
- maximum iterations
- resource limits
- approval requirements

# Worker Response

Workers return structured results.

Example:

```json
{
  "status": "completed",

  "artifacts_created": [
    "patch_v7",
    "test_report_v3"
  ],

  "observations": [
    {
      "type": "implementation_note",
      "message": "OAuth middleware required modification"
    }
  ],

  "recommendations": [
    {
      "type": "invoke_role",
      "role": "qa"
    }
  ]
}
```

## Response Fields

### status

Possible values:

- completed
- failed
- blocked
- awaiting_input

### artifacts_created

References to artifacts generated by the worker.

Workers create artifacts.

Hermes stores and versions them.

### observations

Structured information discovered during execution.

Examples:

- implementation notes
- warnings
- assumptions
- discovered constraints

Observations are informational and do not directly change workflow state.

### recommendations

Suggested future actions.

Workers may recommend actions, but Hermes decides whether they occur.

Example:

Worker response:

```json
{
  "type": "invoke_role",
  "role": "reviewer"
}
```

Hermes decides:

- Should reviewer run?
- When?
- With what inputs?

# Forbidden Worker Behavior

Workers must not:

- modify workflow state directly
- invoke other workers directly
- bypass policy checks
- access unauthorized tools
- persist private state
- assume a specific model implementation

---

# Design Principle

Workers provide cognition.

Hermes provides control.

The worker answers:

> "Given this objective and context, what should be done?"

Hermes answers:

> "What happens next?"
